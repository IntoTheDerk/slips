# SLIP-0027 : Transaction verification statements

```
Number:  SLIP-0027
Title:   Transaction verification statements
Type:    Standard
Status:  Draft
Authors: Petr Susil <petr.susil@satoshilabs.com>
Created: 2026-09-29
```

## Abstract

A transaction verification statement is a commitment to the result of verifying selected outputs of a transaction, or to an observation of external state, which a wallet checks before it authorizes the transaction.
The verification is performed by a party or mechanism which the wallet trusts for that purpose, and which need not be the party that requested the payment.

## Motivation

A wallet can authenticate the destination and the amount of an output, but that does not establish what the output does.
Bitcoin `OP_RETURN` data and EVM calldata are transaction data which an address and an amount do not describe, and whose meaning depends on a protocol the wallet may not implement.
A wallet which cannot establish the effects of such an output can only present it as opaque data or refuse to sign it.

This specification defines a statement, which allows the verification to be performed elsewhere and its result to be checked by the wallet.
The result is not trusted because it accompanies a payment request; it is trusted because the wallet verifies the evidence for it under a trust anchor it holds.

Until the verification succeeds, a result is a claim.

A statement is defined independently of any payment request, so that it can also be used when a transaction is signed without one.
[SLIP-0024](slip-0024.md) carries a statement in a payment request memo.

## Statement

A statement is the concatenation of the following fields:

* *payloadOutputs* (length-prefixed binary string): the outputs to which the statement applies, as the concatenated SHA-256 hashes of their binary encodings. Its length MUST be a multiple of 32 bytes and a hash MUST NOT be repeated.
* *statementHash* (32 bytes): commitment to the verification result, see [Statement hash](#statement-hash).
* *verificationMethod* (4 bytes): 32-bit identifier of the verification method in little-endian byte order, see [Verification methods](#verification-methods).
* *attester* (length-prefixed binary string): identifier of the trust anchor under which the evidence for *statementHash* is verified, see [Evidence](#evidence).
* *verificationData* (length-prefixed binary string): method-specific parameters and evidence. A zero-length string is used if no verification data is included.

All variable-length fields are encoded the same way as in Bitcoin transactions, as a [length-prefixed string](https://en.bitcoin.it/wiki/Protocol_documentation#Variable_length_string), where the length is encoded as a variable-length CompactSize integer.

Several statements MAY apply to the same output.

## Payload

The binary encoding of an output is defined in [SLIP-0024](slip-0024.md), *Signature generation*, and is used here whether or not a payment request is present.

The *payload* is every output of the transaction being signed whose binary-encoding hash appears in *payloadOutputs*, in transaction order.
Identical outputs are selected together; an empty selection is a *state assertion*, whose *payloadHash* is SHA-256 of the empty string.
Every hash in *payloadOutputs* MUST equal the hash of the binary encoding of an output of the transaction being signed, and the wallet MUST reject a statement which does not satisfy this.

```
payloadHash = SHA256(concatenated payload encodings)
```

## Auxiliary data

*Auxiliary data* is the facts outside the payload which the wallet supplies to the verification, namely:

* the *nonce*, an unpredictable challenge issued by the wallet;
* the *coinType*, the SLIP-0044 coin type under which the outputs are interpreted;
* where the statement is carried in a payment request, memos of that payment request which affect the result, such as a coin purchase memo.

The wallet MUST take auxiliary data from its own processing of the transaction and of the payment request, and MUST NOT take it from *verificationData*.
Auxiliary data which can affect the result MUST be committed in the verification context.

## Verification context

The *verification context* is the canonical encoding, defined by the verification method, of the auxiliary data and of every other fact outside the payload which can affect the result.
It MUST determine every such fact and commit to any evidence from which one is established, and transaction facts MUST be checked against the transaction being signed.
It begins with b"\x53\x4c\x27\x43"; if the method defines no method-specific context, only the nonce follows.
Authentication of *statementHash* is separate from the verification context.
The canonical encodings of the verification context and of the result MUST be deterministic, and the result encoding MUST uniquely determine the result.

## Statement hash

```
verificationContextHash = SHA256(verificationContext)
statementHash = SHA256(
    b"\x53\x4c\x27\x53" ||
    verificationMethod ||
    attester ||
    payloadHash ||
    verificationContextHash ||
    verificationResult
)
```

where *verificationMethod* is encoded as a 32-bit little-endian integer, *attester* is length-prefixed and *verificationResult* is the canonical result encoding.
The wallet MUST derive the payload and the verification context itself, and MUST NOT rely on a statement unless its *statementHash* equals the value computed above.

## Evidence

*statementHash* MUST be established by evidence in *verificationData* which the wallet verifies under a trust anchor it holds for the method, such as an attester's signature, a succinct proof or a hardware-attested execution.
*attester* identifies that trust anchor.

## Verification methods

A verification method defines how a statement is verified.

A verification method MUST account for every *security-relevant effect* of the payload — any loss of the payer's assets, or any claim on them or on authority over them, now or later, such as a standing allowance.

A result depends on the payload alone (*interpretation*), on the payload executed against an observed state (*simulation*), or on an observation of mutable state (*dynamic state*); where a result mixes these, the strongest dependence applies. A result is *complete* if it accounts for every security-relevant effect of the payload: an interpretation MUST bound each effect under the semantics the method covers or mark it unbounded; a simulation MUST bound each effect by a condition which transaction validity or execution enforces or mark it unbounded; a dynamic state MUST identify the observed state and the nonce under which it was observed.

A method MUST define:

* the payloads or state assertions to which it applies;
* the meaning of *verificationData* and *attester*;
* the auxiliary data it uses and its encoding in the verification context;
* required evidence and trust anchors;
* the result and its encoding;

## Relying on a statement

A wallet MUST NOT rely on a statement if a fact on which the result depends can change after the wallet's authorization without invalidating it, unless transaction validity or execution enforces that fact.

If a signing workflow produces more than one independently broadcastable authorization, each MUST independently satisfy every statement the wallet relies on.

Where satisfying the payload produces a separate signature, delegation or other reusable authorization, the wallet MUST NOT rely on a statement unless the method commits to that authorization and accounts for its replay scope.

## Requesting a statement

A wallet MAY require a statement for an output which is not bounded by its amount, and MAY request one before it authorizes the transaction.
Where the wallet requests a statement, it issues the nonce which the verification context commits to.
A wallet MUST NOT rely on a statement whose nonce it did not issue or has invalidated, and MUST invalidate the nonce on acceptance.

## Use with SLIP-0024 payment requests

A statement is carried in a [SLIP-0024](slip-0024.md) payment request as a *statement memo*, encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x05\x00\x00\x00" (32-bit encoding of the integer 5 in little-endian byte order).
* *statement* (variable length): the statement, encoded as defined above. Its *payloadOutputs* MUST select requested outputs of the payment request.

The statement memo is included in *paymentRequestDigest* as any other memo. Several statement memos MAY appear in one payment request.

The payment request signature authenticates the inclusion of the statement in the payment request. It does not establish the verification result, which is established by the evidence alone.
The nonce is the payment request nonce and the *coinType* is that of the payment request. A wallet MUST require a nonce which it issued and has not invalidated for a payment request which contains a statement memo, relies on externally authenticated mutable state, or contains an output which is not bounded by its amount, and MUST invalidate the nonce on acceptance.

A wallet MUST refuse a payment request unless every security-relevant property of the transaction is determined by a requested output which the payment request authenticates, or is accounted for by a result whose verification context commits to that property.
